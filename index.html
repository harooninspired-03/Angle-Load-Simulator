Angle Load Simulator

Angle Load Simulator

A test tool that connects many pretend venues to the broker at once and records what each of them receives, so you can check that the roulette angle stream stays smooth when it is shared with many venues.

How it works Start it Settings Reading the output CSV file Results viewer Problems

What it does

Each simulated venue is its own connection to the broker with one subscriber on etg.roulette.angles.<table>. Nothing is drawn. The tool only measures what arrives and when.

Arrival rateMessages per second at each venue. The real stream is about 38.9 a second.
GapsThe wait between two messages. A normal gap is about 26 ms.
DisconnectsA venue whose connection reports an error is counted.
Silent and malformedVenues that received nothing, and messages that are not two floats.

The simulator is a Java program, so it has to be started from a command window on the PC that runs it. This page cannot launch it. Fill in the settings and copy the three steps.

Settings

  
Written as name=value after the class name. Every setting is optional. These are the defaults in the code.

  

    
SettingDefaultWhat it does

    
      
urltcp://192.168.0.34:61616Address of the ActiveMQ broker.

      
table1Table id. Each venue subscribes to etg.roulette.angles.<table>. A wrong id gives silent venues.

      
consumers29How many simulated venues to start. Each one gets its own connection.

      
minutes30How long to run. After that it prints the final summary and exits.

      
intervalSec5Seconds between report lines and CSV rows.

      
rampMs500Pause between starting one venue and the next, so you can watch a real venue as the load grows.

      
expectedHz30Messages per second you expect at each venue. A venue is flagged below 80% of this. The real stream is about 38.9, so 38 is a better value.

      
slowGapMs100A wait between two messages longer than this counts as a slow gap and flags the venue. Normal jitter of 100 to 158 ms trips the default, so 300 is better for finding real stalls.

      
csvnoneFile name for one row per venue per report interval.

PartMeaning

What a healthy run looks like

  
Average rate close to 38.9 a second, worst gap usually under about 60 ms, and flagged=0 most of the time. Gaps of 100 to 158 ms show up now and then and are normal jitter.


  
The final summary

  
When the time is up, or when you press Ctrl+C, it prints one line per venue (messages, slow gaps, worst gap, disconnects, bad messages) and then totals. The last line says RESULT: no disconnects, no silent venues, no malformed messages. only when all three are zero. Slow gaps are not a pass or fail on their own. Compare them with a run that uses fewer venues.

Problems

  

    
You seeLikely reasonWhat to do

    
      
Compile errors about javax.jms or org.apache.activemqThe classpath is empty or points at missing jars. In PowerShell, %CP% does not work.Use the PowerShell steps in PowerShell and the Command Prompt steps in cmd. Check the jar paths exist.

      
failed to start for every venueThe broker is not reachable.Check the URL, that the central server is running, and that port 61616 is not blocked by a firewall.

      
venues that received nothing is above 0The table id is wrong, or the publisher is not sending.Use the id of the table whose angles the real venue shows. Check that the real wheel is running.

      
Disconnects during the runThe broker restarted, or the network dropped.Note the time and compare it with the broker log.

Old time values like 00:05:10 in the CSVOlder version of the file.Use the current version, which writes seconds. The viewer reads both.

    
  


  
What this tool cannot tell you

  
All simulated venues run inside one Java process on one PC. If that PC or process freezes, every simulated venue stalls together, which looks the same as a stall on the broker side. It also measures when a message reaches the listener, not whether an animation looks smooth.


  
What your long run showed

  
In the 15-hour run with 40 venues there were no disconnects and no malformed messages, and the rate held at about 38.9 a second. About once an hour, every venue had one gap of 1043 to 1070 ms in the same 5-second window, and the rate in that window dropped to about 32 a second. The same hourly gap was later seen in the real venue's own log, and in the broker log at times when the simulator was not connected, so the simulator is not the cause.
